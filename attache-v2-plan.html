1What “complex” means in web ML

Not a bigger model — more models, cooperating, in real time.

Single-model inference is table stakes; every LiteRT.js codepen does it. The frontier that actually impresses (and that WebGPU's 5–60× speedups exist for) is three-fold:

  • Cascades — many models in one pipeline, each stage feeding the next, cheap models gating expensive ones;
  • Streams — camera and microphone pipelines where inference keeps pace with reality;
  • Systems — indexes, quantization, worker pools: the infrastructure that makes 100k documents feel like 100.

3Track A — the Verified RAG stack

Retrieval → generation → verification. Five models, one pipeline, zero servers.

Pipelined, not sequential: sentence N verifies on the NLI model while Gemma is still generating sentence N+2. The claim chips flipping green one by one is the demo.

What the user sees

Refunds are debited from your next settlement batch, not your bank account. [1] ✓ entailed 0.94
UPI refunds typically credit within 30 minutes to one business day. [2] ✓ entailed 0.88
Refunds above ₹50,000 require manual approval. ⚠ not supported by any retrieved passage — flagged

The third claim is the money shot: the browser catches its own LLM inventing a policy, before the user can be misled. That is Vitark's core promise, demonstrated in 30 lines of pipeline code.

Architecture changes in the app

  • src/ml/pipeline/ — a declarative stage-graph runner: stages declare inputs/outputs, the runner overlaps execution and feeds the HUD per-stage timings. Replaces the hand-wired search flow.
  • src/ml/scoring/crossEncoder.js + src/ml/verify/nli.js — same provider pattern as v1 (config-driven URLs, quality tiers, honest fallbacks: no cross-encoder → bi-encoder order stands; no NLI → claims render unverified with a badge saying so).
  • Ask view gains a pipeline inspector: a collapsible rail showing each stage's model, backend and ms — the System view's honesty, inlined into the flow.

The honest risk: OCR model selection

Browser-grade OCR on LiteRT is the least-proven link in this plan. Phase B0 evaluates, in order:

  • PaddleOCR v4 det+rec tflite exports (~5 MB + ~11 MB) — best quality/size if the exports run clean on LiteRT.js; needs CTC decode in JS (~60 lines);
  • Keras-OCR / EAST-class tflite alternatives;
  • Fallback: Tesseract.js (WASM, not LiteRT) — keeps the feature shippable while the LiteRT path matures; the provider chain pattern makes the swap invisible to the UI.

Devanagari OCR is explicitly out of scope for v2 (Latin-script first); it becomes a v3 goal with a Hindi-capable recognition model.

Mobile UX spec

  • New Scan action in Library (mobile: prominent camera FAB): full-screen viewfinder, detected quad glows mint when stable, auto-captures after 1 s of stability.
  • Review screen: dewarped page + extracted text side by side; user confirms → indexed with collection: scanned, camera badge in Library.
  • Offline end-to-end once models are cached — the courtroom story, now with a camera.

5The substrate — when search must scale

Both tracks eventually stress v1's brute-force scan (fine to ~20k chunks, measured). The substrate upgrade, built as its own module when triggered: HNSW index in WASM (or a tuned IVF in plain JS — spike decides), int8 vector quantization (4× memory cut, negligible recall loss at 768-d), and a worker-pool embedder (N workers × XNNPACK for bulk indexing; the litert main-thread constraint applies to LiteRT only — quantized scoring and index maintenance parallelize freely). Target: 100k chunks, <10 ms p95 query, index persisted incrementally to IndexedDB.

7Risks, stated plainly

  • Model conversion is the new risk class. v1 only consumed pre-built .tflite files; Track A's cross-encoder and NLI both require litert-torch conversions we haven't exercised. That's why Phase 0 is a hard gate, with score-parity tests against PyTorch — not just "it loads".
  • OCR may land on the WASM fallback. If PaddleOCR exports fight back, v2 ships scan-to-search on Tesseract.js and swaps the provider later — the feature is not hostage to the runtime.
  • Gemma's multi-GB download confines the full Track A demo to desktop/laptop; mobile gets retrieval + verification with generation marked "desktop feature" honestly.
  • Weight budget: v2 adds ~50 MB (cross-encoder + NLI) to the ~186 MB flagship baseline before Gemma. Progressive loading stays first-class: every stage usable the moment its model lands, later stages appear as they arrive.
  • NLI verdicts are probabilistic — the UI must say "not supported by retrieved passages", never "false". Wording is part of the spec, not polish.
